## 0. 明确宿主编排与 MCP 执行的职责

当前 `packages/mcp/src/index.ts` 要求调用方承担创作、组合工具并审核图片，继续沿用这一方式。现有 `workspace-planner.ts` 的可选规划入口保持可选，不扩展为必需的内部自主制作 Agent。

宿主根据用户需求决定分镜、参考职责、生成方式、入出点和修复动作，通过 MCP 工具逐步操作。MCP 负责参数校验、生成服务调用、抽帧、剪辑、渲染、资产管理和执行记录，返回明确结果与可处理的问题。

宿主推进的流程为：需求归一化 → 素材分析 → 目标计划 → 生成请求准备 → 生成 → 素材检查 → 剪辑 → 成片检查 → 局部修复或完成。计划、资产、版本和检查结果保存在服务端；换宿主或恢复会话时先读实际状态，避免只依赖聊天记忆。缺少用户事实或输入时，宿主记录缺口并向用户询问。

Skill 保留精简的导演方法、工作流导航和失败修复原则；完整导演内容通过服务端 `craft_get` 按需读取，resources 提供另一入口，本地参考文档可作为带版本的分发副本。能力规格、模板、项目状态和审核记录以服务端当前合同为准。模式对应的提示词模板、输入绑定、确定性约束和版本校验由 MCP 实现。语义视觉检查优先由具备相应能力的宿主读取实际图像/片段后完成；纯文本宿主需用户或另一个明确可用的视觉审核方式，未检查时保留待审核状态。现有模型分析工具继续可用，不把自主内部视觉验收作为本轮前置条件。

Skill 负责解释创作方法、工具使用顺序和如何判断证据；MCP 负责可执行的约束。不能仅靠 Skill 提醒来保证素材范围、参数兼容、引用一致性或审核版本有效，这些条件必须由公共服务校验。宿主审核记录是判断依据，不能把它误称为工具自行看过画面。

用户主要确认创作方向、缺失事实、关键歧义和已有规则要求的费用。宿主默认自行检查完整提示词预览，不强制用户逐镜批准技术文本。MCP sampling 不作为必要依赖；后续可按实际客户端能力协商增加，不能假定各宿主都支持。读取文档、预检、查询结果均不得隐式触发新的付费分析或生成。

验收：宿主可通过 Skill 和 MCP 完成规划、检查、剪辑及修复；检查工具确实向支持图像的宿主提供像素；无视觉能力时不伪造通过；切换宿主或重连可通过服务端记录继续同一项目。

## 1. 建立独立的目标制作计划

当前 `reference_storyboard_prepare` 以唯一 `sourceShotId` 选择镜头，`reference_adapt` 遍历全部参考镜头建立目标场景。它适合一对一替换，但不适合作为所有创作的通用中间结构。现有编辑器可以拆分、移动场景；缺的是这些操作之前独立的目标设计。

扩展现有版本化 `ProductionPlan`，由 `production_plan_validate` 校验、`production_plan_save` 保存、`production_shot_prompts` 读取目标镜头生成草稿。文字创作、模板和参考分析都可产生这个结构。简单字幕修改继续走已有编辑接口，不要求多做一套分镜。P0 先支持连续产品演示所需字段；P1 扩展其他镜头类型与关系表达。

- `target`：成片画幅、总时长要求（精确值/范围/自由）、音频与字幕要求；区分用户硬性要求与宿主规划建议。
- `shots`：独立的目标镜头 ID、叙事目的、主体、起始状态、有序动作阶段、结束状态、运镜、声音要求和验收条件。每镜一个主要叙事目标，允许“拿起→倾斜→倒入→放回”等多个动作阶段；静态展示允许无动作阶段。镜头类型、动作类别和生成模式分别定义，不把“反应镜头”当成模型接口。
- `sourceEvidence`：可为空、可多个，保存来源镜头/时间范围/分析版本，仅供溯源。允许一个参考镜头拆成多个目标镜头，也允许合并、重排或补充目标镜头。
- `entities` 和 `continuity`：复用现有人物/品牌档案，描述跨镜头物体状态、关系及变化；状态保留 `unknown`。连接类型区分连续、插入画面、时间跳跃等。
- `references`：在现有角色上补充 `usage`、`transfer`、`preserve`、`exclude`。`analysis_only` 素材不进入生成请求；动作迁移和运镜迁移分别声明。允许同一产品图约束颜色、外形和标签等多个相容属性，要求职责明确且无冲突，不机械限制“一张图只能提供一个事实”。需要片段输入时保存实际截片资产及来源范围。
- `productionScope`：正式制作任务的目标、所需检查及允许的素材用途由服务端保存并关联项目/请求。保留独立素材实验入口；实验素材进入正式项目时仍需映射到目标镜头并通过适用检查，不能用客户端临时标志解除正式项目约束。

校验器检查声明之间的矛盾，例如同一连续事件中一个物体的结束状态与下一镜起始状态冲突。不能把文字状态一致当成画面真实一致，也不能规定所有视频都遵守一种物体叠加顺序。未确认的视觉关系交给审核，不能默认通过。

必填字段只保证数据存在。字段应附具体示例和不合格示例；“自然”“保持一致”等空泛描述应提示补充。对缺失证据允许 `unknown` 并返回后续检查任务，不能诱导宿主编造准备动作或完成状态。参考观察和目标改写分别保存，例如把“挤酱”改成“盖面包”后，要重新决定原片是否还适合作为动作输入。

改动位置：新增 contracts/core 的计划结构与校验；让现有 `reference-tools.ts`、`storyboard-tools.ts` 转接到公共服务；扩展 `creative-context.ts`，保留现有接口兼容。

验收：无参考输入能建计划；支持来源与目标多对多映射；修改来源分析不覆盖目标设计；连续状态矛盾有定位信息，明确时间跳跃不会被误拒绝。

## 2. 将模型目录升级为规格协商

当前 Provider 已接入声明参数校验。继续补齐模型能力驱动的参数组合与输出规格协商，不把固定档案作为创作能力的上限；计费设计单独后置。P0 验证首个目标场景必需的实际档案，P1 扩展更多已验证模型与组合。

建议扩展模型档案，声明经过验证的可选值、组合限制、默认值和规格继承关系。例如某接口的输出比例来自显式参数，另一个来自首帧，源视频编辑的时长则来自源视频。缺失元数据应视为未知。

扩展现有 `generation_prepare`，在实际生成/上传前完成预检，返回：

- 满足目标规格和输入职责的可用档案，以及不满足的具体条件。
- 最终规范化请求、预计输出规格、裁切或留边方案。
- 明确的阻断项、提示项和可修复选项；不调用生成服务。

官方模式允许查询模型目录与兼容性元数据，不能把“预检”描述成绝不联网；不得因此开始媒体上传或付费模型调用。模型目录中未知的参数不能靠提示词猜测支持。

本轮目标支持经过验证的动态参数组合，旧固定档案作为兼容输入。用户明确选择的模型保持优先；自动选择仍优先兼容的 MiniMax。不存在兼容模型时报告缺口，不冒充可用或静默换模型。

画幅不一致不应一律拒绝。明确的留边、画中画、设计好的裁切可能合理。需要拒绝的是违反硬性目标、且没有明确适配方案的请求。几何裁切比例可确定计算，主体是否被裁掉则需要视觉证据。

复用输入哈希、参考资产快照及幂等机制。准备阶段保存服务端记录并返回 `preparedRequestId`、版本和请求哈希，绑定计划/镜头版本、模板/编译器版本、实际模型档案版本、完整提示词、参数、素材哈希及 Provider 输入映射。生成凭据和临时访问令牌不写入预览。参考顺序、提示词、规格或有效依赖改变，旧准备记录不能继续作为可提交凭证。实际提交与 worker 调用前均校验，避免宿主手工拼接成另一份请求。

已有 `quote_create`、`reference_storyboard_quote` 和 `job_submit` 适配该准备记录，继续使用已有报价、用户同意和幂等机制；这属于请求一致性，不新增价格体系或支付流程。已有报价需要适配未支持的新参数时应明确报告兼容性缺口，不能按旧配置报价、按新配置生成。官方入口的合同/转发变更列为 rikoko-platform 依赖，计费设计仍另行处理。

生成结束按实测时长/尺寸核对承诺规格，不能只信档案。素材与诊断结果一并保留；规格不合格不等于网络作业失败，也不能以此自动重新付费生成。

改动位置：`contracts/src/generation.ts`、operation schema、`providers/src/config.ts`、`providers/src/index.ts`、`generation-input.ts`、`core/src/index.ts`、worker、MCP capabilities。官方模式需要 rikoko-platform 同步参数合同和请求转发；这属于功能兼容，计费设计另行处理。

验收：不支持的组合在提交前被拒绝；预览和实际提交使用同一规范化请求；输入变更使旧准备结果失效；产物规格偏差形成质量问题，但保留已生成资产。

## 3. 提示词编译必须与模式、输入和目标计划一致

当前已有 `core/src/production-prompts.ts`、`generation_prompt_preview` 和 `production_shot_prompts`；旧 `reference-prompts.ts` 路径仍会读取原片状态。需要将这些路径统一接入目标计划和实际模式，避免多套模板各自演进，或把原片状态当成目标状态。

保留 `generation_prompt_preview` 的纯预览用途，并由 `generation_prepare` 完成最终组装、绑定和保存。未指定实际模型的草稿必须标明不可直接提交。模板按“通用约束＋模型/接口措辞＋镜头类型内容”组合，减少整份复制：

1. 输入目标镜头、实际模式、参考绑定、模型档案与创作约束。
2. 根据模式选择自己撰写的措辞模板；文生视频、图片编辑、首帧、首尾帧、参考生成、源视频编辑分别处理。动作/运镜迁移是参考使用策略，不自动宣称为新模型接口。
3. 输出 Provider 适配后的提示词、参考编号映射、使用的目标约束、未解决冲突和模板版本。
4. 保存预览内容，实际提交使用该冻结结果，不能提交时再生成另一版文本。

宿主 Agent 可以编写或覆盖提示词，覆盖必须记录原因、基础模板版本、最终文本和差异。MCP 仍验证实际输入存在、模式兼容及强制约束；覆盖原因不能解除参数、审核、素材绑定或既有费用授权边界。原片说明先经过目标设计，不原样强制继承。安全指令留在宿主及数据处理边界，视频提示词集中描述画面和声音。

模板为服务端版本化资产，自行撰写并通过样例验证；“固定措辞”不等于模型必然遵守。远端服务更新影响随后准备的新请求，已保存请求不自动重编译。本地安装和自托管实例需要升级或显式同步；记录模板、合同与服务版本，不能承诺一次更新所有宿主立即生效。

同步打通分镜首尾帧路径：起始图、结束图分别审核和绑定，并明确两者职责。对无需先出图的受支持任务，不强迫先调用图片生成。

验收：无首帧请求不生成首帧措辞；无尾帧不能提交首尾帧请求；参考编号与实际 Provider 数组一一对应；源视频仅供分析时不上传；预览与提交内容哈希一致。

## 4. 暴露通用媒体检查工具

扩展现有 `media_inspect`。P0 保留资产 ID 入口并补齐关键区间采样与证据覆盖；项目版本可由已渲染资产解析。P1 增加更丰富的对比和音视频片段读取。复用当前 FFmpeg 抽帧、切片与探测代码，支持：

- 首/中/尾帧、指定时刻、切点两侧、有限密度的网格图。
- 相邻镜头边界并排、原图与目标裁切预览并排。
- 动作相关区间的短片段；音频相关问题可取得对应可试听片段。
- 实测时长、尺寸、帧率信息、黑场/冻结候选、画面变化测量。

参考与目标对比优先按动作阶段或已确认事件对齐，不默认把相同秒数当成相同动作。采样要覆盖接触、落位、盖合等关键事件前后；无法定位事件时，宿主先请求更密集的受限采样或片段。P0 至少提供这一按需复查路径，不把三帧检查直接当成完整动作验收。

输出既要有结构化时间映射，也要在 MCP `content` 中提供宿主可直接接收的图片内容。只有资产 ID、URL 或 JSON，不能保证多模态宿主已经看到了像素。分析、分镜和作业完成结果可附少量已有检查图，并返回精确的 `media_inspect` 调用参数；轮询不重复发送所有图像。短片段通过宿主支持的媒体读取方式或受控链接提供；高分辨率和大量帧按需读取，缓存键绑定资产哈希、真实时间、检查参数和工具版本。

必须区分请求采样时间与实际解码帧时间；无法取得准确帧时间时标记估算或容差，不能把 `-ss` 的请求位置当成已验证的帧时间。检查证据的生成/持久化也要如实标注工具副作用；“不生成新创作素材”不等于完全不写入本地记录。

帧差只用于标记“静止结论可疑”或“疑似冻结”，不能证明动作完成或判断动作类别；运镜、闪光、压缩都可能造成变化。首尾帧也不足以验收完整动作，需要看相关时间区间。明确标出未覆盖区间，检查工具本身不声称已完成语义审核。

改动位置：扩展 `packages/core/src/media-inspection.ts` 和 `packages/mcp/src/production-tools.ts`，复用 `core/src/reference-media.ts`、`render/src/reference-timing.ts`；完善 `mcp/src/index.ts` 的结果序列化及现有资产权限和宿主媒体支持。

验收：对支持的格式和大小范围内的导入或生成视频返回带时间信息与资产哈希的图像证据；超限有明确诊断和可行的分段检查方法；采样受上限约束且可继续读取；在支持图片的宿主中确认实际像素可读取；宿主保存检查依据，纯文本宿主未取得有效视觉审核时返回待审核状态。

## 5. 建立素材感知的剪辑决策

不建议把“默认使用参考时长”直接替换成“全部使用素材全长”。后者仍会把预留空镜、失败动作或多余尾段带进成片，也可能破坏明确的总时长和语音节奏。

建议以现有 `sourceStartMs`、`durationMs`、`speed` 为执行层，新增显式选择策略：

- `full_asset`：采用实际可用素材范围，仅在没有冲突的硬时长要求时作为保守草稿。
- `selected_range`：采用经查看的入点、出点，可附动作/台词锚点和证据。
- `fit_target`：为明确目标时长选择剪辑、变速或重新规划；冲突必须显式返回。

区分参考时间、生成素材时间、成片时间。源素材范围长度除以速度才是成片时长，并按帧边界做明确量化。已实现的字幕、词锚点、音效和音量包络编辑逻辑继续复用。

新增本地预检报告：头尾舍弃长度、越界情况、裁切比例、字幕/音频锚点影响。长尾被舍弃只是提示；若舍弃区间与已确认的动作/台词完成锚点冲突，才构成确定性阻断。未知完成点进入视觉检查。

改动位置：`reference-tools.ts`、`storyboard-tools.ts`、`core/src/editing.ts`、`workspace-contracts.ts`、`workspace.ts`；不必重写渲染器。

验收：不再无提示继承原片秒数；短素材不越界，长素材不静默丢尾；精确总时长要求不会被自动延长；变速后的字幕与事件仍保持对齐。

## 6. 分开作业完成与验收完成，并支持局部修复

保留现有 `job.status`，完善独立质量状态 `unreviewed / needs_changes / accepted`，让 `workspace_result` 返回两者以及问题列表、证据引用和下一步动作。

扩展现有 `workspace_validate`（本地预检）及 `media_review`（记录实际审核），图片、片段、成片共用审核结构：

- 审核绑定资产哈希、计划版本、项目 revision、检查范围和适用条件，避免换素材或改剪辑后沿用旧通过状态。
- 检查结果区分确定性测量、宿主视觉判断、用户判断和明确调用的模型分析；每项允许通过、失败、未知、不适用。语义审核需关联实际检查的媒体与范围，不能仅凭文字计划确认画面合格。
- 记录实际证据与判断依据。记录声明只能提高可追溯性，不能保证审核者判断正确。
- 更改素材、构图、时序时使相关审核失效；无关字幕修改不必使原素材的身份审核失效，但成片排版仍需复核。

检查记录存在不等于宿主真的看过或判断正确。服务端能校验证据归属、范围、版本和必需检查是否齐备，不能把这些条件包装成自动语义识别。逐项 `unknown` 保持待审核；`not_applicable` 必须有理由，不能让宿主用填 `true` 表示不适用。动作完成点要绑定素材时间和审核证据，之后才可用区间计算判断剪辑是否截断。

显式区分媒体场景、设计图形场景和草稿占位。历史汉堡审计记录了无素材片尾出现 `LOCAL COMPOSITION` 默认图形的问题；当前源码已增加图形场景声明，需用回归验证区分是否有效。不能把所有无素材场景都禁止：明确设计的文字卡/品牌卡可以交付；未解决的占位必须在正式交付时阻断。

草稿仍可渲染、预览和导出，明确标注质量状态；正式交付要求相关检查通过。`workspace_result` 查询不应隐式触发新分析或生成，也不能隐藏有问题但可用于修复的产物。

公共服务保存制作范围并在生成准备、现有报价/提交、worker 执行及正式交付边界重验适用约束。`workspace_commit`、`revision_create/revise`、模板、Studio 和宿主导出不能形成绕过路径。引用外部或实验素材可以进入草稿，但正式交付仍检查目标匹配、证据和审核；不能要求调用方只要填写某个工具名就天然可信。

保持三种状态各自清楚：`job.status` 表示执行进度；`quality.status` 表示审核状态；`finalReady` 表示所有适用交付条件是否满足。技术错误存在时，单独一条 accepted 审核不能令 `finalReady=true`。草稿链接和正式交付链接/标记不能混淆；下载链接的发放及后续读取边界均需核对版本和用途，不能只在导出按钮校验。

问题条目提供 sceneId、时间范围、条件 ID、证据和建议修复动作。先使用已有 trim、fit、字幕、音频编辑；需要重生成时只重做受影响的素材并沿用其他已接受结果。复用现有幂等键和作业恢复，设置明确的重试上限、停止条件和失败原因，避免重复提交或无限重试。

改动位置：`core/src/delivery.ts`、`workspace.ts`、`mcp/src/tools.ts`、`presentation.ts`、worker、contracts 和 Python 图形场景分支。验证服务应被 MCP、Studio 和正式导出路径共同调用，避免只在 Skill 中要求。

验收：未检查成片返回 unreviewed；占位不能正式交付；明确图形卡不误拦截；修改已审核相关内容会失效；只修改一个镜头时其他生成资产可复用。

## 7. 分阶段指导、知识分发和反馈

### 7.1 决策点返回短指导

为分析读取、计划校验、请求准备、素材完成和成片预检增加统一的简短结果字段：`stage`、`status`、`blockingIssues`、`warnings`、`unknowns`、`nextActions`、`guidance`、`knowledgeVersion`。问题需带镜头/字段/时间范围、证据和可调用的修复步骤；建议限制在当前阶段最相关的两三条。兼容现有返回结构，不强行改写所有工具。

例如目标动作是盖面包、引用声明为挤酱时，返回冲突位置和重新选择参考的操作，而非泛泛提示“注意连续性”。枚举/声明冲突可判定；画面实际动作仍需证据。分析失败应返回版本或字段诊断并保留已准备素材，不能教宿主删除必要字段或绕过分析。源片缺少收尾时标记缺失，目标补拍是创作决定。

### 7.2 精简全局说明，按需读取知识

server instructions 保留身份与流程、少量创作原则，以及费用、事实边界、同一会话交付和工作台链接的简短底线。细则放对应工具描述与服务端校验。Skill 保留目标设计、参考职责、检查和修复方法，避免变成只有“听服务端的”的空入口。

原则应准确：参考可作为观察证据，也可在用户明确要求时约束节奏；成片时长由用户要求、叙事节奏和素材实际完成点共同决定；各输入职责明确且相容；目标状态先设计；未查看的画面保持未审核。

新增只读 `craft_get(topic, stage, problemCode?, version?)`，返回短规则、正反例、适用条件、版本与必要引用；新增 `rikoko://craft/...` resources 读取同一内容。resources 的自动读取和 prompts 的展示由宿主决定，工具兜底不能省略。P0 先在相关结果中提供最少指导；P1 完善知识库和本地分发。

官方能力事实、模板、用户偏好与单次观察分开存储。禁止把一次输出尺寸泛化为模型规格，禁止把绕过分析写成标准恢复流程；本地经验与当前能力目录冲突时返回依据。服务端知识集中管理能减少漂移，不能保证宿主永远不记录错误经验。

新增 `skills/rikoko/references/` 后同步改 `scripts/clients.ts` 和发布打包清单，校验整个文档包可安装、引用不失效，并保留用户自定义内容。本地副本、服务端文档与模板标明版本兼容关系，所有措辞自行撰写，不复制竞品文本。

现有云端分析协议握手已在 `cloud-client/src/analysis-protocol.ts` 实现，生成规格与审核合同可沿用同样的版本协商思路。兼容性错误应返回缺失特性与受影响步骤，宿主不能通过删除必要字段绕过去。

### 7.3 最小反馈和回归从 P0 开始

扩展 `feedback_add`，保存素材/镜头/计划/成片版本、准备请求及模板版本、接受或拒绝原因和审核来源。复用已有作业记录统计技术失败、质量问题、重做次数、实际用量和耗时；用户审美偏好单列，不等同于客观质量判定。不要求用户每次填写长表，宿主可依据真实反馈记录，未给原因则保持未知。

固定回归包含汉堡组装，以及独立的动作完成、身份保持、时长/画幅和图形卡场景。所有失败和未完成结果进入分母，不能只统计用户最终接受的产物。按模型、任务类型、参数、候选数、模板版本和手写覆盖情况分组，防止把换模型或增加重试误认为模板提升。统计界面可后置，原始关联记录不能后补猜测。

### 7.4 验证层级

验证覆盖三类：

| 层级 | 覆盖 | 能证明什么 |
| --- | --- | --- |
| 宿主集成回归 | Skill 完整安装、图片/片段读取、无视觉能力时的待审核状态、断线重连、不同宿主续接项目 | 宿主能编排并检查，MCP 能返回证据、保留状态与约束；未看画面不伪造通过 |
| 协议/本地媒体回归 | 纯文字任务、无参考任务、首帧/首尾帧、动作/运镜引用、精确时长、自由时长、横竖混排、图形卡、语音字幕、未知状态、旧版本恢复 | 工具可调用、参数和证据不丢失、无静默裁切、检查及失效规则生效 |
| 真实质量评估 | 多类内容和多个实例；相同模型、规格和候选数量的对照，记录随机种子或重复样本条件 | 在给定样本中，动作完成、身份一致、构图、音画对齐、合格镜头比例及返工次数是否改善 |

固定措辞和新流程不能凭单次出片保证画质。工程验收与真实生成效果必须分别报告。

## 8. 优先级、依赖与阶段退出条件

优先级表示分批实施和交付顺序。用户已授权逐步修改；阶段退出仍按下面的验收证据判定，已有本地实现也必须经过同样检查，不能因开始实施而将其标记为全部完成。

| 编号 | 优先级与范围 | 依赖和退出条件 |

## 11. 改造后的宿主编排流程

1. 宿主读取 `capabilities`，恢复已有请求/项目；只为缺失事实或素材提问，遵守用户时长、画幅、模型偏好和已有费用授权。
2. 需要参考理解时完成分析及报告读取，检查关键图像和覆盖缺口；分析未完成时保留问题，不把下载/切段成功当成分析成功。
3. 宿主设计目标计划，使用 `production_plan_validate/save` 保存目标状态、动作阶段、引用职责及验收条件；无需参考的任务也走同一目标结构，简单编辑可复用现有计划。
4. 宿主调用 `production_shot_prompts` 或 `generation_prompt_preview` 制定草稿，由 `generation_prepare` 解析实际模型、参数和参考，返回完整请求预览。宿主核对，必要时按原因覆盖；用户不必逐镜审阅技术提示词。
5. 在实际需要付费时，沿用现有报价与用户同意流程，提交已准备请求。服务端重验版本与绑定，worker 使用相同请求；不在提交时换模板或模型。
6. 生成完成后返回实测规格、质量状态和检查入口；宿主调用 `media_inspect` 读取首尾及关键动作区间，使用 `media_review` 记录真实判断。失败则定位问题并选择修复，未看保持未审核。
7. 宿主依据实际动作/台词完成点选择入出点和适配方案，通过 `reference_adapt` 或已有编辑接口保存 composition；用 `workspace_validate` 检查素材范围、锚点、裁切和占位。
8. 渲染草稿，宿主检查最终画面、相邻镜头及适用的音频/字幕，并记录绑定当前 revision 的审核。修复只涉及有问题的范围；相关旧审核失效。重做受已有授权和明确次数/用量限制约束。
9. 正式交付边界重新确认 `finalReady`；未通过仍可返回标明质量状态的草稿和问题。完成时在原会话交付视频与工具返回的准确工作台链接，不自动打开浏览器。
10. 将用户实际反馈及审核问题关联到模板、请求与素材，作为下次模板/流程评估的证据。服务端保存状态，换宿主可续接。

## 12. 兼容、发布与范围边界

所有新合同增量版本化，旧项目不静默改时长或构图；旧审核缺失即标记未审核，不能自动升级为通过。服务端模板更新只影响新准备请求；本地运行时、Skill 文档包、官方网关与宿主能力分别记录版本与验收状态。

rikoko MCP 仓库负责协议、本地服务、剪辑工作台、媒体处理和公共运行时。rikoko-platform 只在官方合同/转发兼容确有需要时作为独立依赖列出，官网、官方模板发布后台和新增计费能力不在本轮范围。

后续实施继续使用当前已有分支，保留工作区已有修改；创建任何新分支需用户另行明确授权。本方案不代表所有实现已完成或所有验收已通过；提交、推送、部署及实际宿主生效状态以各批次记录为准。
