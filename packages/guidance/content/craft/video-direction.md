# Video direction with the host agent

## Interpret a reference and design a target

<!-- director:reference -->
Explain which observable relationship makes the reference effective: what first attracts attention, what changes, why the next event follows, whose reaction matters, and how the ending pays off the opening. Cite source shots/evidence, distinguish observation from inference, and keep audio or continuous movement unknown unless actually observed. Decide which relationships serve the new intent and which must change; a source description is not yet a target direction. Do not substitute shot counts, cut timestamps or an analysis summary for that explanation.

For an ad, a hand contacting a latch before it opens may establish the product's function. For dialogue, the listener's pause may reveal more than the speaker's words. For a landscape montage, a shift in scale and sound may create the progression without physical causality. Preserve the useful relationship, not the incidental subject's appearance. New goals may require a new order or duration; a faithful source edit inherits the requested structure.

Give each shot a purpose and a visible change: initial arrangement, initiating action, contact or response when applicable, and the settled result. Track who speaks, who listens, the reaction, gaze and screen positions across cuts. Keep object count, support and completed actions coherent for realistic scenes; explicitly intentional surreal behavior follows the work's own logic. Separate shot count from generation-request count: group or split for performance continuity, model capability and cost, then verify actual events and turns. No universal shot duration or one-shot-per-request rule.

Existing saved legacy plans and frozen jobs retain their previous contract. Unknown observations remain questions for the host; do not parse arbitrary prose with a keyword detector and call it verified orientation.

## Optional shot outline and continuation aids

These practical options are adapted from the user-provided private notes “画面生成操作笔记（2025.9–2026.10）”, which summarize the private “总爆款库”. Original prompts, sample videos and some image-only instructions are unavailable in the notes. The methods are practitioner observations, not independently verified or rikoko-tested guarantees; apply them selectively within the user's brief and actual model capabilities.

Before expanding a complicated scene into generation direction, it can help to outline each shot in plain terms: intended duration; shot size or viewpoint; who is on which side and facing where; foreground and its focus; background and lighting; the main action in order; and the intended end pose or state. The first-frame description captures the initial still; the video direction describes the change from that state. Use lens or timing numbers only when they serve the shot and the selected interface; the source's examples are not universal defaults. When reviewing a poor result, identify whether arrangement, framing, reference conflict or action complexity is the likely problem, then revise that element if a repair is authorized. Do not simplify or change source choreography when the user requires it preserved.

For a continuous multi-clip scene, choose or prepare a boundary image that actually makes the next starting state legible. A wider view can help record who is on each side; a closer view can make a seated posture, hand placement or contact with a chair visible. Avoid complete front-to-back overlap if it hides the positions needed for continuation. Check gaze, screen side, posture, props and scene geometry against the actual end of the previous clip. If a deliberately different view is used as a layout aid, verify the view and state rather than assuming the next model will preserve both. An existing end frame may be sufficient; the note's suggestion of a brief extra spatial record is a creative option, not a promise that a model can produce an extra frame or a requirement to add generation time. See `craft/image-direction` for the optional line-art repair when an otherwise useful continuation frame contains conflicting appearance.

When a movement must remain visibly continuous, such as a jump and landing, consider keeping the connected action in one generation if the model and duration support it. A cut, different plan or other treatment can be appropriate when they do not. Do not assume a single request guarantees continuity.

## Write the generated scene once

Prefer `shot.sceneDirection` for new video plans: one complete paragraph describing the visible subject and setting, starting arrangement, current operation, completion timing, settled result and camera. The compiler uses this paragraph instead of separately restating subject, setting, initialState, action/actionStages, endState and camera. Those structured fields remain saved for continuity checks, host inspection and boundary-image prompts; keep the paragraph consistent with them. The service checks binding and structure, not semantic equivalence.

Give each sentence a job. Put absent components and support relationships at the point where they matter ("the top bun is outside the frame", "the lower bun supports the patty before release"). Name a completion time within the actual requested generation duration, leaving time for a visible hold; an edit duration and a generated duration may differ. Avoid generic stages such as "establish, perform, complete, hold": identify the real contact, motion and stop instead. Do not borrow the next shot's operation.

Keep reference instructions limited to what that particular asset supplies in this shot. A lowering excerpt should not also be assigned cooking and topping. State appearance-only use once in the image reference instruction. Use `productFactIndices` to append only facts not already expressed in the scene; an explicit `[]` keeps all canonical product facts in the plan without repeating them in the prompt. `generationConstraints`, process requirements, chosen kit text, necessary audio/ending direction and reference bindings still enter the prompt. Avoid restating them in the paragraph unless essential to explain the action. Inspect the assembled prompt as one scene, not as a checklist.

No automatic shortening or truncation is applied to authored prose. If the prompt is too long, remove duplication or split the shot while preserving required action and state. Old plans without `sceneDirection` keep their structured wording. First/last-frame drafts always use their respective structured states and never inherit the video's action paragraph. Read `capabilities.generationPreparation.supportedTemplateVersions` for `rikoko-scene-direction-v1`; older local/cloud runtimes need updating before using this field.

Before generation, translate the user's purpose into target shots. Source shot count, cuts and seconds are observations, not a required target timeline. Use `production_plan_validate` and `production_plan_save`; assign stable target shot IDs, one main action, initial state and final state. Source shot IDs can be empty or many-to-many. Name persistent objects consistently. Use `unknown` when evidence is missing and explain intentional time jumps.

For every new video brief, import the current attachments and save `workspace_request_save` with the user's actual message and asset IDs, even when no inputs are missing. Compare their returned content hashes with any existing plan before resuming it. Save the plan with `request={requestId,expectedVersion}` using that request's version. Every attached asset must appear in shot references or in `request.excludedAssets=[{assetId,reason}]` with an explicit task-based explanation. Original videos cannot be excluded; an analysis_only image does not substitute for the video. Do not exclude the requested product just to reuse an old plan. The binding is retained on plan edits and rechecked before generation; updated requests or changed bytes require reconciliation and preparation again. Existing legacy plans remain readable, but a new user brief must not silently inherit them without this binding.

For processes, music-led work or advertisements, also use production quality (`rikoko_guide {topic:"production-quality"}`). Establish object inventory/support before writing prose; budget the approach, contact, completion and settle within the shot. Declare any skipped process step as an intentional time jump and anchor its resulting state. Work backward from the film's purpose, soundtrack strategy and ending rather than preserving reference shot count. Host choices such as a logo card or exact shot count are not user requirements unless the user actually supplied them.

Choose inputs by responsibility:

| Input              | Responsibility                                     |
| ------------------ | -------------------------------------------------- |
| Character image    | Identity, wardrobe, physical features              |
| Product image      | Geometry, visible markings, material and color     |
| Scene/style image  | Only the declared setting or appearance properties |
| First/last frame   | Actual boundary states and framing                 |
| Motion excerpt     | Explicitly selected action, camera path or rhythm  |
| Source observation | Understanding; no generation input unless selected |

Save each media shot's `referenceChoice={strategy,reason}`: `motion_reference` for movement, `stage_first_frame` for stage/count/layout control, or `direct` when existing appearance inputs/text suffice. Keep the reason within 240 characters. Read `referenceChecks` during validation and `referenceCheck` during preparation. These host records never enter provider prompts; missing choices remain visible on legacy plans. A finished-product image cannot establish an unfinished stage. For state anchoring, reuse a suitable existing image or actual previous end frame before generating anything. Check it once with shot-bound `startingStateChecks` (see visual-review). Video preparation checks the chosen route against actual mode/references; boundary-image preparation remains available before the anchor exists.

For each source-linked media shot, use `sourceVideo={strategy:"reference",assetId:"actual-source-or-excerpt-id"}` and include that video in shot.references as generation role motion (with transfer and instruction) or source_video. Importing or analyzing the original alone does not send it to the video model. A local excerpt must be produced by the runtime extractor and cover every selected source-shot interval (or the explicit method segment intersection). Cloud execution requires the original bytes or a cloud-verified excerpt; a host claim about an arbitrary uploaded clip is insufficient. If the model cannot accept that video, stop with the capability gap and select a compatible interface. Do not downgrade to stills, text reconstruction, or analysis_only to make the task pass. Reconstruction plans remain readable but cannot bypass source video delivery.

A source frame is opt-in using `useSourceComposition=true`; target product and scene references normally establish the image. Motion extraction requires `motionPurpose` and `motionExclusions`. Do not use an unrelated operation as an action reference. Compare action types in `generation_prompt_preview` and resolve mismatch warnings.

When the user specifically wants the source's actions, camera moves or pacing with a different product, first evaluate a compatible reference_to_video profile under the face policy (Seedance Mini for face-free tasks, otherwise MiniMax or user-selected Kling) with the current product image and corresponding motion excerpt. State which properties each reference supplies and exclude the source product, text and audio where appropriate. First-frame/first-last-frame inputs may supplement a compatible video-reference interface; they cannot replace the source video for a request containing a video. Preserve visible worker/character participation and the intended gag while fixing physical continuity. A series of static holds or skipped operations is a creative change, not an equivalent reconstruction. Do not assume more intermediate image generations or more constraints improve fidelity.

Use `production_shot_prompts` to carry the saved target states into image and video prompt drafts. Inspect actual first/last frames before relying on them. `generation_prompt_preview` supports distinct text, first-frame, first/last-frame, reference, motion-transfer and camera-transfer wording. Transfer modes are prompt strategies: the selected provider must still expose a compatible `reference_to_video` input route. Use its returned prompt and ordered reference bindings. Do not paste cloud analysis JSON into a video prompt.

For protocol `rikoko-prepared-generation-v1`, pass `request={requestId,expectedVersion}` from the saved original brief (a bound plan may carry this link). Call `generation_prepare` with `input` containing the exact preview prompt, model, ordered reference asset IDs/roles, supported `parameters` and `target={width,height,aspectPolicy:"match"}`. Also pass the preview's normalized `direction`. For a saved target shot, pass `plan={planId,expectedVersion,shotId,stage:"video"}` with `production_shot_prompts.video.direction`. For boundary images use `stage:"first_frame"` with `.image.direction` or `stage:"last_frame"` with `.lastFrame.direction` and an image model. First-frame drafts describe only the starting state; completed-action requirements belong to the video. Changes to target action/states/references belong in the plan first. For non-remake work, handwritten or changed wording requires `promptOverride.reason`; this does not waive mode, parameter, target or reference checks. Set a direction reference's `usage="analysis_only"` when it must not enter the provider request.

Check `capabilities` for `allowedParameters`; do not invent upstream fields. First/last-frame aspect comes from the image. A mismatch requires fixing the image/parameter or an intentional `contain`/`allow_crop` policy. A preparation saves the exact logical operation, full prompt, template/compiler versions, plan dependency, reference hashes, provider field/array ordering and model configuration digest. The preview shows public output controls; private provider configuration is hash-bound, and temporary delivery URLs are resolved only at execution. Check `readyForSubmission`. Cloud preparation negotiates `rikoko-cloud-preparation-v1`: the server previews declared reference hashes/metadata without uploading files, then quotation uploads and verifies actual bytes into an immutable bound request. Older gateways fail with `PREPARATION_PROTOCOL_UNSUPPORTED`; keep the preparation fields and reconnect a compatible server.

Pass the returned `input` unchanged, including `preparedRequestId`, directly to `job_submit` without `quoteId`. The server performs internal pricing and settlement. `quote_create` and `reference_storyboard_quote(preparedRequestId=...)` are optional estimates only when the user asks for pricing. Read it after reconnection with `record_get(type="generation-preparation",id=...)`. Quotation, submission and the worker recheck dependencies without recompiling saved wording. Dependency changes require a fresh preparation; retrying the same submitted job uses its original idempotency key. Reference-input video generation requires preparation by default; all video generation requires target dimensions. Only an administrator setting `RIKOKO_ALLOW_LEGACY_GENERATION=true` may enable legacy unprepared generation. It never disables storyboard target-plan requirements. Final AI review is not required for delivery. No model calls occur during preview/preparation; preparation persists an account-owned record (and a cloud draft in official mode) and needs write permission. Model availability, provider calls and billing remain separate.

Saving a target plan creates a default scoped project (`productionProjectId`). Preparation with that plan inherits the scope and canvas automatically. To attach an existing project or change review requirements, call `production_scope_save` with its plan ID/version and current scope version (`0` initially). Use `input.production={projectId,scopeVersion,shotId}` together with the matching preparation plan. Scope is saved on the project and cannot be disabled on individual requests. Updating a bound plan/scope synchronizes its version to the connected cloud before saving; reconnect the original connection if synchronization is unavailable.

Quickly check critical images once; completed videos need no visual acceptance. Call `production_asset_assign` for the exact project, scope and shot. `use="prepared_generation"` requires completed output prepared for that target. Imported or experimental media needs `use="external"` and explicit permission in scope `requirements.allowedAssetUses`. Use `reference_adapt` with `plan={planId,expectedVersion}` and `replacements[].productionShotId`; it assembles target shots in plan order and returns the scoped `projectId`. Pass it to the first `workspace_commit`. Source-only IDs must map unambiguously. Existing scenes can use `scenePatchSchema` through `revision_revise`. Planned title cards must declare shot `visualKind="graphic"`. Scope changes invalidate assignments and revision acceptance. Use `workspace_result(purpose="final")` to deliver after technical checks; it requires no final AI review. Inspect actual footage and the final cut within available observation capabilities. Preserve unknowns and keep formal acceptance distinct from delivery; never automatically regenerate for quality.

After generation, use the measured clip metadata; observe actual content against the shot purpose within available capabilities. Keep its full duration by default. `reference_adapt` uses complete replacement videos unless you specify a selected range or `timingPolicy="fit_target"` with a target duration. Fit changes whole-clip playback speed within 0.25–4. Choose cuts from the action, not the reference stopwatch. Keep a short readable settled result. When self-checking temporal edits, verify audio, captions and effects within available capabilities; do not carry obsolete word timing onto replaced speech.

Only repair the user-requested shot or edit, or work covered by an explicit remaining repair allowance; never automatically regenerate after quality judgment. Preserve accepted media and prior versions. Report what is observed, what is inferred and what remains unknown.

## Gemini-to-host remake handoff

1. Obtain a completed Gemini `recreate` report (merge prepared segments when needed). Read `reference_analysis_get(section="handoff")` through all pages. The default `handoffDetail="compact"` retains full selected-shot observations, narrative roles, unknowns/gaps and evidence IDs/confidence, but omits repeated evidence prose/events/segment summaries and reduces neighbors to boundary states. Use its `detailsAccess` arguments (without the `tool` key), or paginated `evidence/events/parts/speech`, when supporting a claim needs the omitted observation or audio. `handoffDetail="full"` restores the detailed view without another analysis call. Retain `binding.analysisAssetId` and `binding.analysisSha256`; processing windows and estimated timestamps do not dictate target cuts.
2. Author `plan.remake` with the binding, `productFacts` supplied by the user or supported target assets, and `requirements`. Each requirement has a stable `id`, `mode` (`preserve`, `adapt`, `free`), `origin` (`reference` or `user`), `description`, `sourceShotIds`, and `evidenceIds`. Reference requirements need both source shots and observed evidence. Preserve the required mechanism/outcome; adapt the stated feature with an explanation; free permits change and need not map to a target shot. These are host declarations, not automatic semantic judgments.
   Record inferred creative choices in target purpose/rationale, not as invented `origin="user"` requirements. A source observation limited to one analysis window is not evidence about the entire video's ending or absent later action.
3. Each target shot needs `purpose`, `initialState`, `action`, `actionStages`, `endState`, `camera`, `acceptanceCriteria`, and `requirementUses=[{requirementId,application,changeReason?}]`. All preserve/adapt requirements must be covered; adapt requires a reason. Source mapping may split or combine shots; together the mapped target shots must cover the requirement's source shots. New target shots may have empty source mapping. Do not copy unsupported product mechanisms from the reference.
4. Relevant coverage gaps block production. Relevant unknowns require Gemini reinspection, or `unknownDecisions=[{index,disposition:"not_applicable",reason}]` explaining why they do not affect this remake. `blocking` remains blocking. A host explanation never turns unseen action into verified evidence. Retain the original report; use a new bound report for reinspection.
5. Validate/save, bind the formal project scope, and compile with `production_shot_prompts`. Its handoff contains source evidence, selected requirements and neighboring target states. Do not add neighboring actions to this shot. Remake generation requires the exact compiled prompt; change the plan to revise it. Source/requirement/product-fact/uncertainty changes need `remake.changeReason`, a new plan version, scope binding, preparation and acceptance.
6. As part of directing, recheck relevant requirements and shot criteria against actual generated media and the rendered cut. For rendered-cut `media_review(revisionId=...)`, supply `requirementChecks=[{requirementId,status:"pass"|"fail"|"unknown",reason}]`; all preserve/adapt requirements must pass before claiming optional acceptance. This does not gate delivery. Use `unknown` when you cannot see. Report protocol validation separately from visual fidelity; only a capable reviewer can judge the latter.

The local service verifies owned report bytes/hash, completed analysis lineage, source metadata/hash and selected evidence. Cloud protocol `rikoko-cloud-preparation-v2` receives the immutable original request, full normalized analysis (and component reports), host plan and exact prompt. It independently matches reports to completed analysis jobs in that cloud account. Source video declarations must be bound to uploaded bytes with the same hash before quote/submit. Both endpoints must be upgraded; older clients cannot drop preparation fields to continue. Analysis is still a model interpretation, not a guarantee of correct classification or movement.

Use `generation_trace_get({id})` with a preparation, job, or returned error `details.generationTraceId` to diagnose stages separately. Compare raw provider analysis when retained, normalized source observations, host-authored plan, compiled provider prompt, actual video field/hash bindings, and worker preflight/execution. Identify the first stage that diverges; do not attribute a host-invented action to Gemini. Historical missing evidence remains null. Preserve humor, interaction, performance and sound timing; visible jewelry or products alone do not establish advertising intent. A plan must explain intentional changes separately from observed source facts.
